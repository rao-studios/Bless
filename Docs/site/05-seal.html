What does the seal sign?

On a signature that names the exact words a reviewer read and sent.

A reviewer holds a private key on their own device. Every ruling they give is signed with it, and the Gate checks the signature against the public key the petition names. A ruling the reviewer did not sign is refused when the policy requires seals, which it does by default.

The bytes, field by field

The seal signs a fixed byte layout, bless/verdict/1. It holds the petition and the reviewer, the ruling with its text, the digest of the words the reviewer read, the note and the moment it was issued. Each string is written with its length, so no two verdicts can share their bytes.

The layout is Bless's own, not JSON: a JSON encoder's bytes have changed between versions of Foundation, and a signature must outlive them. Every timestamp is whole milliseconds, so a verdict read back from disk signs exactly as it did.

Anyone can check it

The signature is Ed25519, so any standard verifier accepts it: Web Crypto above, Python's cryptography package in the integration guide, CryptoKit in the tests. A release carries its verdicts, so the clinic, an auditor or the patient's own app can check who allowed the words and that the words are the ones sent.

For engineers: where each piece lives
  • The seal-signs trail runs from the reviewer's identity to the release's own check.
  • CryptoKit's Ed25519 signatures are randomized: two seals over the same verdict differ, and both verify. SiteFixturesTests checks the fixture's seal by verifying it.
  • Bless keeps no revocation list: when a reviewer leaves, the host stops naming their key.
