What is a petition?

On what Bless keeps while a reply waits, and what it works out from it.

A petition is a reply held for review. It keeps the model's proposed text, the conversation the reviewer may see, the recipient, the reviewers, the policy, and every verdict given so far. It never changes the proposed text: an amendment is a verdict, kept beside it.

Derived, not stored

What the recipient would get is worked out each time it is read: the latest amendment, or the proposed text. So is its SHA-256, and so is the list of blessings that count. A field that is derived cannot drift from the facts it comes from.

Five standings, one of them open

A petition stands in one of five places: pending, blessed, withheld, expired, withdrawn. Only the first is open. Every other standing is final, and a final petition accepts no verdict.

Two standings allow a release. A blessed petition releases the blessed or amended text. An expired one releases a fixed holding message, and only when its policy names one.

Only the context the policy allows

The Gate keeps only as much of the conversation as the policy's context window allows, and never the system prompt. The reviewer sees what they need to judge the reply. The store keeps no more than that.

For engineers: where each piece lives
  • Petition is a value: its rules, applying(_:at:) and lapsed(at:), return a new petition and are tested in PetitionTests with no Gate.
  • Petitions are kept in memory, or as one private file each by FilePetitionStore, sealed with AES-GCM when given a key.
  • A petition's JSON is in the integration guide, with a release's and a ledger event's.
